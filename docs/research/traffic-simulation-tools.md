# Code-first traffic simulation for a Porto pilot

Research date: 28 October 2026. Scope: selecting an existing simulation engine and identifying the work needed to turn it into a repeatable tool for comparing bus-reliability interventions, costs, and delivery phases. This is desk research, not a calibrated Porto model or a completed simulation.

## Recommendation

**Start with Eclipse SUMO and build a Python scenario-and-report layer around it.** This is a recommendation based on the user's preference for code control and a small real-city pilot: SUMO combines command-line execution, OpenStreetMap import, GTFS import, public-transport stops and schedules, programmable traffic lights, and machine-readable outputs. Those capabilities fit corridor experiments such as bus lanes, junction changes, conditional signal priority, and revised dwell/holding assumptions. [SUMO simulator](https://eclipse.dev/sumo/docs/sumo.html), [OSM import](https://eclipse.dev/sumo/docs/Networks/Import/OpenStreetMap.html), [GTFS import](https://eclipse.dev/sumo/docs/Tools/Import/GTFS.html), [public transport](https://eclipse.dev/sumo/docs/Simulation/Public_Transport.html), [traffic lights](https://eclipse.dev/sumo/docs/Simulation/Traffic_Lights.html).

**Aimsun Next is the strongest commercial alternative to evaluate**, especially if a local partner already holds an Aimsun model and licences. It has a documented console without a UI, Python scripting, OSM and GTFS import, and run-time APIs. PTV Vissim is another credible professional option, particularly where an existing Vissim/Visum model or signal-controller integration is available; its Python COM automation is Windows based. [Aimsun console](https://docs.aimsun.io/next/24.0.4/UsersManual/CommandLine.html), [Aimsun importers](https://docs.aimsun.io/next/26.0.2/UsersManual/ImportersAndExporters.html), [Aimsun extensibility](https://docs.aimsun.io/next/latest/UsersManual/AimsunNextExtendibility.html), [Vissim scripting](https://cgi.ptvgroup.com/vision-help/VISSIM_2026_EN-DE/en-us/Content/15_Schnittstellen/Scripting.htm).

**The full requested workflow is a product layer, not just a simulator choice.** The reviewed documentation verifies simulation, scenario editing, statistics, and programming interfaces. It does not establish a turnkey capability that takes an arbitrary reliability target and produces an engineering-verified, locally priced, phased works programme. Treat target search, intervention definitions, cost evidence, phase dependencies, and report generation as explicit project components. Existing features can supply parts of these: AnyLogic has native optimization experiments, and Aimsun Plus advertises appraisal/reporting and construction-staging applications, discussed below. This is a synthesis of the reviewed capabilities, not a claim that every commercial module has been exhaustively ruled out.

## SUMO: the important implementation details

### A city map is a starting network, not observed traffic

`netconvert` imports OSM and `osmWebWizard.py` can generate a quick scenario. However, missing speed/lane information may be inferred, nearby junctions may need joining, and imported signal layouts need checking. A visually plausible imported street map must not be presented as a faithful baseline. [SUMO OSM import documentation](https://eclipse.dev/sumo/docs/Networks/Import/OpenStreetMap.html).

Demand is a separate input: routes, origin/destination matrices, turning ratios, counts, or other observations. SUMO provides `od2trips`, routing tools, and `routeSampler`. The latter can select routes to match observations, but its documentation warns that counts often admit many different route distributions. Matching counts alone does not identify the true OD demand. [Demand modelling](https://eclipse.dev/sumo/docs/Demand/Introduction_to_demand_modelling_in_SUMO.html), [routeSampler and quality control](https://eclipse.dev/sumo/docs/Tools/Turns.html).

### Bus punctuality is directly measurable

SUMO can define scheduled arrival times, departure constraints, dwell, passengers and stops. Its `arrival` stop attribute enables `arrivalDelay` in stop output and the `traci.vehicle.getStopArrivalDelay` function. This is a concrete path to measuring lateness rather than substituting average car speed for bus performance. [SUMO public transport](https://eclipse.dev/sumo/docs/Simulation/Public_Transport.html).

`gtfs2pt.py` imports transit data for a specified date. Depending on inputs, it can use fastest paths between stops or incorporate OSM transit routes; the documentation explicitly describes route import as limited. Validate paths and stop placement, particularly after clipping a corridor. A GTFS timetable imports intended service, not observed bus reliability. [SUMO GTFS importer](https://eclipse.dev/sumo/docs/Tools/Import/GTFS.html).

The traffic-light documentation includes a bus-prioritisation example and supports external control through TraCI, including phase duration and programme changes. That enables a custom rule such as prioritising a late bus while respecting bounded green extensions. Pedestrian clearance and compatible transitions must be represented in the controller; do not optimise raw green states without those constraints. [SUMO traffic-light control](https://eclipse.dev/sumo/docs/Simulation/Traffic_Lights.html).

### Repeatable experiments need no computer-use automation

The `sumo` executable runs a scenario from the command line. Outputs include stop records and aggregated edge/lane statistics. Python can launch one process per scenario/seed and parse the output. Use TraCI when a run-time controller is needed; otherwise a static configuration plus CLI is simpler. [SUMO CLI and output options](https://eclipse.dev/sumo/docs/sumo.html).

`libsumo` exposes a similar API in-process and avoids TraCI's socket overhead. Python parallel instances require multiprocessing, and GUI/multiple-client behaviour differs. Benchmark it only after correctness is established; the choice is not necessary to prove the pilot. [libsumo documentation](https://eclipse.dev/sumo/docs/Libsumo.html).

## Commercial alternatives: concrete caveats

### Aimsun Next

The distinction between scripting and the API matters: Python scripting automates model preparation/editing, whereas the API changes behaviour during simulation. Official API examples include bus priority at a junction and phase-timing changes. [Extensibility](https://docs.aimsun.io/next/latest/UsersManual/AimsunNextExtendibility.html), [API examples](https://docs.aimsun.com/next/26.0.0/UsersManual/ApiMicroExamples.html).

The GTFS importer can import stops, lines and timetables incrementally, select a subnetwork and service date, and optionally use shapes and dwell offsets. This reduces input work but still requires a correctly georeferenced road network and mapping checks. [Aimsun GTFS importer](https://docs.aimsun.com/next/26.0.0/UsersManual/GTFSImporter.html).

`aconsole` supports loading a project, running a target replication, and executing Python without a graphical window. The 24.0.4 manual says console is available with Pro, Advanced and Expert annual subscriptions. Confirm current edition/API rights rather than assuming every downloaded trial or Lite licence is suitable for batch jobs. [Command line](https://docs.aimsun.io/next/24.0.4/UsersManual/CommandLine.html), [console availability](https://docs.aimsun.io/next/24.0.4/UsersManual/ScriptExecute.html).

Current public standard prices are **€2,000 Lite, €3,500 Pro, €5,500 Advanced, and €7,500 Expert per seat/year**. The pricing page states two concurrent sessions on one computer per seat. These are software list prices, not study or construction budgets; obtain a scoped quote including API, console, concurrency, hosting and support. [Aimsun editions and prices](https://www.aimsun.com/aimsun-next-editions-prices/).

### Aimsun Start and Aimsun Plus: reducing setup and appraisal work

**Aimsun Start** is particularly relevant to the wish to replicate a city easily. The vendor offers a ready-to-calibrate model for any city, combining network geometry and TomTom-derived OD matrices, an automated TomTom/GTFS pipeline, and optional public-transport/control-system integration. This is a vendor-described delivery service, not a verified self-service Python API or an already calibrated Porto model. Request a scoped Porto corridor offer with data dates, bus integration, calibration responsibilities and reuse rights; public service pricing and an automated ordering/API workflow were not established. [Aimsun Start](https://www.aimsun.com/aimsun-start/)

**Aimsun Plus** explicitly advertises cost-benefit analysis, standardized reporting and construction-staging analysis; its Toronto example evaluates alternative project sequences and their traffic impacts. These are existing professional workflows that could reduce custom work. The public description does not establish automatic Porto bills of quantities, locally sourced prices or automatic generation of a buildable phased scheme from a punctuality target. Obtain a demonstration of the exact intended report rather than assuming those capabilities are included. [Aimsun Plus](https://www.aimsun.com/aimsun-plus/)

### PTV Vissim / Visum

Vissim has professional public-transport priority and external signal-controller workflows. Its COM interface exposes attributes, but not every attribute is writable. External Python automation runs as a separate Windows process using COM; that is an automation route, not a cross-platform headless executable equivalent to SUMO. [Vissim capabilities](https://www.ptvgroup.com/en/product_description_ptv_vissim_en.pdf), [current scripting documentation](https://cgi.ptvgroup.com/vision-help/VISSIM_2026_EN-DE/en-us/Content/15_Schnittstellen/Scripting.htm).

For city creation, the verified pipeline is **Visum OSM/GTFS import → Vissim ANM transfer**, or Vissim OpenDRIVE import. Whether the required transit timetable objects transfer with adequate fidelity must be checked in a proof of concept; the existence of importers is not evidence that every object survives unchanged. [Visum exchange formats](https://www.ptvgroup.com/en/products/ptv-visum/faqs), [Vissim imports](https://cgi.ptvgroup.com/vision-help/VISSIM_2025_ENG/Content/5_Netzbearbeiten/Import_Netz.htm).

PTV says commercial pricing is quote based. Its documented demo restrictions include no COM, no saving, no evaluations, and a simulation-duration limit. A free viewer/demo therefore cannot validate the desired automation workflow. Licence terms and parallel workers need a vendor quote. [Vissim licensing FAQ](https://www.ptvgroup.com/en/products/ptv-vissim/faqs), [demo limitations](https://cgi.ptvgroup.com/vision-help/VISSIM_2024_ENG/Content/License-mgt/Demo-version-info.htm).

## Open-source licence and ecosystem notes

- **SUMO:** EPL-2.0, with GPL v2-or-later as a secondary option; bundled optional dependencies and imported map data have their own terms. [Downloads/licensing](https://eclipse.dev/sumo/docs/Downloads.html), [dependency/data licences](https://eclipse.dev/sumo/docs/Libraries_Licenses.html).
- **MATSim core:** GPL v2-or-later. PT2MATSim provides standalone Java tools and library integration for GTFS/HAFAS/OSM transit conversion and network mapping. A realistic person-demand model remains a separate modelling input. [Core licence](https://raw.githubusercontent.com/matsim-org/matsim-libs/main/matsim/LICENSE), [PT2MATSim](https://github.com/matsim-org/pt2matsim), [MATSim modules](https://github.com/matsim-org/matsim-libs).
- **CityFlow:** Apache-2.0; oriented toward multi-agent traffic-signal control experiments. [Maintainer repository](https://github.com/cityflow-project/CityFlow).
- **UXsim:** MIT; Python macroscopic/mesoscopic modelling and analysis, with optional accelerated execution. Its aggregate design makes it an interesting screening model, while detailed bus-stop interactions would require separate validation. [Maintainer repository](https://github.com/toruseo/UXsim).

## Existing cities and Porto precedent

Real-city simulations are well established. SUMO's official catalogue links reusable scenarios including Luxembourg (LuST), Monaco (MoST), Ingolstadt, Turin, and others. It also distinguishes obsolete/synthetic scenarios and includes a 24-hour car-traffic dataset covering Lisbon among five cities. Those are useful pipeline references; their demand, scope and age must be checked before reuse. A Lisbon car model is not a Porto bus model. [SUMO scenario catalogue](https://eclipse.dev/sumo/docs/Data/Scenarios.html).

MATSim lists open scenarios such as Berlin, Hamburg, Munich, Paris/Île-de-France, Mexico City and Santiago. Its catalogue warns that some entries provide only part of the inputs required to run a model. [MATSim open models](https://www.matsim.org/install/open-data-models/).

There is direct **historical Porto bus precedent**: Shi, Steenkiste and Veloso's 2018 paper built a central-Porto SUMO network using STCP information and OSM, reporting 136 routes, 855 stops and 5,723 weekday bus trips. Its passenger demand was inferred from older taxi trajectories, so it demonstrates feasibility, not a validated description of today's bus demand. A current runnable scenario, licence and calibration package were not verified in this research. [Author-hosted paper, section IV](https://www.cs.cmu.edu/~mmv/papers/18itsc-ShiSteVel.pdf).

An ISEP dissertation also simulated the Circunvalação/Amial junction and compared pedestrian-crossing alternatives in SUMO. This is another local precedent, not evidence of a maintained city model ready for the pilot. [ISEP dissertation](https://recipp.ipp.pt/bitstream/10400.22/19809/1/DM_MarianaBrito_2021_MEEC.pdf).

## Two alternatives for easier scenario design

### A/B Street

A/B Street explicitly targets editing streets and intersections and communicating alternatives. Its downloadable application can import an arbitrary GeoJSON boundary; the same workflow is available through `cli one-step-import`. The importer documentation says that GTFS, parking and person/trip demand require further data beyond OSM and are not standard across cities. Importing Porto's roads therefore does not automatically import today's traffic or bus operations. [Project overview](https://github.com/a-b-street/abstreet), [city import](https://a-b-street.github.io/docs/user/new_city.html).

It can run without graphics: its HTTP/JSON API loads scenarios, changes signals, exports edits and returns trip/throughput metrics; Python examples are provided. The documentation labels the API under construction with no backward-compatibility guarantee. Buses are simulated, but stop-level punctuality/holding/TSP functionality comparable to the intended calibrated SUMO pilot was not established. The repository's 2025 update says the project has evolved into several other planning tools. Evaluate a small import and scripted comparison before relying on this as the long-term engine. [Headless API](https://a-b-street.github.io/docs/tech/dev/api.html), [simulation scope](https://a-b-street.github.io/docs/tech/trafficsim/index.html), [maintainer status](https://github.com/a-b-street/abstreet).

### AnyLogic

AnyLogic supports detailed roads, intersections, bus stops and traffic controls. **GIS routing and Road Traffic lane simulation are distinct workflows.** Its automatic shapefile conversion initially creates all roads as two-way with two lanes in each direction and ignores speed limits and other road-rule information. Those attributes need correction; a map import is not a faithful lane network. Road networks can also be generated through Java, although the documented network topology cannot be changed after initialization. [Road Traffic Library](https://www.anylogic.com/features/libraries/road-traffic-library/), [shapefile conversion limitations](https://anylogic.help/online/markup/converting-roads.html), [Java network generation](https://anylogic.help/markup/create-road-network-by-code.html).

It **does natively support optimization experiments**, including Genetic/OptQuest engines, objectives, constraints, replications and Java control. Professional supports standalone Java export and command-line export; its Cloud Python API documents execution without animation and parameter variation with replications. Export/optimizer/Cloud entitlements need checking for the chosen edition. This is a real reduction in custom experiment orchestration, although a Porto baseline, intervention choices, local unit rates and construction-phase dependencies remain model inputs rather than automatically discovered facts. [Optimization](https://anylogic.help/anylogic/experiments/optimization.html), [standalone export](https://anylogic.help/anylogic/running/export-java-application.html), [Cloud Python API](https://anylogic.help/cloud/api/python.html), [edition matrix](https://www.anylogic.help/anylogic/ui/editions.html).

## Porto open-data enrichment

These two user-supplied sources serve complementary roles: the Urban Platform explains operational data pipelines and the municipal open-data catalogue exposes downloadable resources. The probes below distinguish descriptions, accessible records and suitability for a particular study date.

### What the Urban Platform adds

The [Urban Platform action page, mobility case](https://plataformaurbana.porto.digital/acao/#AVPGM) identifies **MobiDash**, induction-loop sensors, `TrafficFlowObserved`, bus movement, road alerts, and historical storage in a Data Lake. It describes NGSI-LD access for the municipal mobility application; floating-car-data integration is described as work in progress. The environmental and shared-mobility cases also describe observations and historical storage. This establishes a relevant institutional data pipeline, **not public access to every underlying history**. The page was retrieved successfully through Python HTTP despite the web reader being unable to open it. The public broker tested below serves **NGSI v2**; its existence does not verify a public NGSI-LD temporal endpoint. [Platform cases](https://plataformaurbana.porto.digital/acao/)

A useful next request to Porto Digital is therefore specific: the pilot area's historical induction-loop observations, sensor/lane/direction mapping and quality flags; recent matching bus observations; and the history/export access conditions. The platform description makes that a supported lead, rather than a guess that counts might exist.

### Municipal catalogue: directly verified inventory

Inspected on **28 October 2026** through read-only HTTP/API code. The public [CKAN `package_search` API](https://dadosabertos.cm-porto.pt/api/3/action/package_search?rows=1000) returned **69 datasets**. This is a verified catalog snapshot, not a claim that the municipality has only 69 datasets institutionally. No standalone traffic count, speed, turning-movement or OD dataset title was found in that catalog; those measurements require the Urban Platform investigation or another source.

The following GeoJSON resources returned HTTP 200 and were fully parsed. Feature counts describe the exports, not unique physical facilities, complete city coverage or certified current conditions. ### How these data should enter the simulation

This is a proposed ingestion design:

1. **Discover through CKAN, then inspect each resource.** Query the [catalogue API](https://dadosabertos.cm-porto.pt/api/3/action/package_search?rows=1000) and retain dataset/resource identifiers, publisher, licence, declared update frequency and download links. Catalogue modification dates, HTTP modification dates and observation/validity dates are different checks.
2. **Build the network from OSM plus municipal GIS.** Match implemented bus corridors, parking/loading areas, access controls and cycling/crossing layers to simulator edges and junctions. Review direction, state and time-of-day fields; preserve unresolved or null values. Use municipal geometry as evidence for correcting OSM rather than assuming it is an immediately runnable traffic graph.
3. **Keep immutable observations and a study date.** Store source URL, retrieved time, observed/valid interval, coordinates, quality flags and content hash. Normalize timestamps to UTC while interpreting local operating rules in `Europe/Lisbon`, including daylight-saving transitions. Never silently combine 2021 counts, a September 2026 timetable and October bus locations as one observed baseline.
4. **Translate only supported measurements.** Use matching counts for demand calibration, map-matched AVL for bus movement/actual stop-event estimation, and explicit validity intervals for restrictions. Use weather and environmental readings as context or validation targets for a separately justified environmental model. Parking supply does not reveal parking demand, and loading-space geometry does not reveal blocking frequency.
5. **Reject stale/ambiguous inputs or label their role.** Define freshness and completeness thresholds per input and decision. A historical snapshot may support an illustrative example or a correctly matched historical study; it cannot establish current conditions. A live observation collector can build future history if publisher terms permit it, but it cannot recover past events that are absent from public feeds.
6. **Retain a data-quality appendix in every report.** Show source/date alignment, spatial coverage, missingness, stock-versus-observation distinctions, licences and assumptions. The operator/municipality request should focus on remaining gaps: current compatible GTFS, historical traffic and AVL exports, controller timings/offsets, turning counts and boarding/dwell observations.

All discovery and probes in this extension used code and direct HTTP. The published CKAN and NGSI endpoints are sufficient for a code-first ingestion prototype; no MCP or computer-use automation is required for these verified resources.

## Recommended Porto pilot and acceptance gates

This section is a **proposed engineering workflow**, not a vendor capability or a claim that the listed interventions are appropriate for a particular Porto street.

Start with one roughly **2–4 km bus corridor**, two or three relevant services, and enough surrounding streets and upstream approaches to capture queues and diversion. These sizes are scoping suggestions. Select the corridor after inspecting data availability and observed bus delay; choose a study date with a known road layout. A small clipped network still needs realistic bus arrival lateness at its boundaries, rather than spawning every bus on time at the corridor entrance.

1. **Build an inspectable demonstration.** Import streets, define stops and routes, and add explicitly synthetic traffic profiles. It answers whether the pipeline works. Label every result illustrative until observation-based calibration passes.
2. **Establish the baseline.** Load matching schedules, measured demand profiles and signal plans. Include bus dwell distributions, initial lateness, vehicle classes and route choices. Use separate days or periods for calibration and validation. Retain the raw inputs, transformations, hashes, simulator version and seed list.
3. **Define success before searching.** An example target is at least 90% of bus arrivals at specified control points within a declared early/late window, while preventing early departures. The window and 90% are examples, not STCP standards. Also measure headway variability, passenger waiting and journey time, missed service, queues and spillback. Count cancelled/unserved/unfinished trips and stop calls explicitly so a scenario cannot improve its score by omitting bad outcomes.
4. **Run a bounded intervention catalogue.** Compare baseline; revised signal timings; signal priority conditional on bus lateness; peak-only or permanent bus lanes; queue jumps where physically feasible; parking/loading enforcement; stop layout or dwell changes; and holding/dispatch measures. Test individual changes and combinations, including plausible implementation constraints. A lane-permission change alone does not represent enforcement, construction or an accessible stop redesign.
5. **Compare distributions.** Use paired baseline/alternative runs with controlled randomness, then vary traffic demand, dwell, bus entry lateness and incidents. Start with a modest replication batch and determine additional runs from result variance and a declared precision target. Report uncertainty and validation residuals, not only an average improvement. FHWA describes field-based calibration and variance-based selection of run counts. [FHWA calibration guidance](https://www.fhwa.dot.gov/publications/research/operations/13026/007.cfm)
6. **Rank feasible packages.** Keep a Pareto set across reliability, passenger benefit, cost and disruption; select a package against explicit priorities and constraints. Reject options violating physical/controller constraints, pedestrian crossing requirements, accessibility or unacceptable queue spillback. Safety feasibility needs engineering review; a traffic-flow result is not a crash-safety certification.
7. **Test a cumulative rollout.** Simulate each intermediate operating stage and, where material, the construction stage. Measure the field trial, update assumptions and rerun before committing to permanent works.

For observation-based traffic generation, SUMO's `routeSampler.py` can fit candidate routes to edge counts, turning counts and origin–destination counts. Its documentation explicitly warns that incomplete counts leave an underdetermined problem: several demand patterns can fit the same observations. Use plausible routes plus independent travel-time/queue checks. [SUMO routeSampler](https://sumo.dlr.de/docs/Tools/Turns.html)

A meaningful baseline gate is therefore a documented fit to **bus travel-time and lateness distributions as well as traffic counts and queues**. Agree tolerances appropriate to the decision and available field variability. Do not invent a universal calibration threshold or claim that one animation establishes validity.

## How to deliver the requested report, costs and phases

The reporting product should separate measured facts, simulation estimates and planning assumptions. A useful generated report has:

- **Baseline and evidence:** study boundary/date, data coverage and age, missing inputs, calibration/validation results and limitations.
- **Exact changes:** locations and quantities of altered lanes, stops and junctions; signal/operational rules; machine-readable scenario diff; maps and affected services.
- **Results and tradeoffs:** on-time proportion, lateness percentiles, headways, passenger time, road queues, displaced traffic and completed service; variation across seeds and demand cases. Link every table/chart to its run IDs.
- **Implementation estimate:** bill of quantities and unit-rate evidence; capital costs, recurring operations/maintenance, data/software/integration and monitoring costs; ranges, exclusions, price date and VAT treatment. Keep project development costs separate from street implementation costs.
- **Delivery sequence:** dependencies, responsible organization, feasibility/design tasks, stage budgets, expected incremental benefits, disruption, decision gates and monitoring/rollback criteria.

### A defensible cost layer

**Recommended design:** link each intervention to a parameterized bill of quantities, e.g. lane-marking length/area, signs, separators, kerb or platform works, signal-controller changes, bus detection, communications, design, traffic management and monitoring. Geometry-derived quantities are preliminary until checked against survey/design information.

Use sourced low/base/high rates and record the source date, geography, scope, units, inclusions and confidence. Distinguish a supplier quotation, a tender estimate, an awarded contract and an actual final cost; a lump-sum corridor contract is not automatically a unit rate for bus-lane paint. Allow unknown costs explicitly rather than filling them with an LLM estimate. Model annual enforcement, maintenance and any additional bus operating requirements separately from capital works. Report a consistent price basis and avoid adding an arbitrary universal contingency percentage.

Portugal's official procurement data is accessible through downloadable XLSX/JSON data on dados.gov.pt; IMPIC describes weekly bulk publication and a token-based API, obtained by request, with daily updates. This provides a code-first route for building a comparable-contract catalogue. It does not guarantee detailed bills of quantities in every record. [IMPIC/BASE access guidance](https://www.base.gov.pt/Base4/pt/documentacao/formas-de-obter-dados-sobre-os-contratos-publicos/), [official API documentation](https://www.base.gov.pt/APIBase2)

A credible detailed estimate needs the selected corridor and design scope. No verified Porto construction unit rates, project budget or delivery duration are supplied by this research.

### Example of a staged package

| Stage | Possible scope, subject to results | Gate before proceeding |
|---|---|---|
| 0 — Observe and validate | Obtain matching schedules and operational data; audit the network; reproduce baseline delays. | Model adequately represents the observations needed for this decision. |
| 1 — Operational trial | Feasible signal retiming, targeted loading/enforcement or dispatch changes. | Measured reliability gain, manageable queues, operational/controller feasibility. |
| 2 — Temporary street trial | Temporary peak bus priority, markings/separators and feasible stop adjustments. | Trial confirms benefits and access/crossing performance; recurring enforcement is funded. |
| 3 — Permanent works | Permanent lane/stop geometry, controller/detection upgrades and civil works justified by the trial. | Detailed design, costs, approvals and implementation resources established. |
| 4 — Extend and monitor | Extend to adjacent corridors and recalibrate affected network behavior. | Benefits persist across days and seasons without unacceptable displacement. |

This is a decision framework, not a prescribed order: some operational changes require hardware first, and some corridors may meet the target without permanent works. The simulator cannot prove how many phases are required. The planning layer must search **sequences** as well as final configurations, obeying dependencies and available budgets. Do not add isolated intervention savings together; rerun the cumulative package. For broader city planning, EU SUMP guidance is a relevant process reference, rather than a source of street-specific engineering costs. [EU SUMP Guidelines](https://urban-mobility-observatory.transport.ec.europa.eu/sustainable-urban-mobility-plans/guidelines-developing-and-implementing-sustainable-urban-mobility-plan-0_en)

## Suggested code-first product architecture

**Recommendation:** keep the simulation engine behind a small, reproducible Python workflow. Proposed components below are application design, not existing SUMO commands.

```text
OSM + GTFS + observed traffic/AVL + signals
                ↓
versioned baseline + validation report
                ↓
structured interventions + goals + constraints + cost catalogue
                ↓
scenario generation → headless simulation batches → KPI extraction
                ↓
feasible Pareto alternatives → cumulative stage simulations
                ↓
HTML/PDF/Markdown report + CSV results + input/run manifests
```

Start with functions/CLI commands for importing a district, validating a baseline, applying interventions, running a batch, comparing scenarios and rendering the report. Keep scenario definitions in JSON/YAML and results in ordinary files or a queryable database. Prefer native batch/CLI and Python APIs; add an application REST API when a map-based editor or remote workers justify it.

An optional MCP server can later expose those same coarse operations, e.g. `create_scenario`, `validate_baseline`, `run_experiment`, `compare_scenarios`, `generate_report`. Return job IDs and artifact paths for long runs. Keep native APIs underneath and put artifact provenance, input validation and reproducibility in the application layer. No MCP dependency is necessary for the first pilot, and no official simulator MCP integration was established in this research.

Use an LLM for explaining sourced scenario changes and assembling narrative from calculated results. Numerical benefits, costs, rankings and stage dependencies should come from explicit data and rules. The first useful deliverable is **one reproducible, validated corridor comparison with a traceable report**, before building automatic city-wide search or a large map-editing interface.

## Evidence limits and procurement questions

- No simulator was installed or benchmarked; no claim here establishes performance on the user's computer or a particular Porto network.
- Porto's live bus endpoint, timetable archive, signal inventory, municipal GIS exports, road-restriction archives and public broker types were inspected. Selected bus/weather/noise observations were recent; traffic observations and the timetable were stale. A calibrated baseline, current compatible timetable, recent matching traffic/AVL histories, controller plans, stop-level reliability and local construction rates remain unresolved inputs.
- Public API access and an entity type name do not establish complete coverage, historical retention, current validity or service guarantees. Dataset licences are recorded per source; the restriction catalogue entries have no declared licence in the inspected metadata.
- Several vendor interface references are version-specific (including Aimsun 24 and PTV 2024/2025 alongside newer documentation). Verify them against the release and licence used in a proof of concept.
- Before buying software, request a scripted demonstration that imports the intended corridor and service date, runs unattended, applies bus priority, produces stop-level lateness and network impacts, and repeats across independent workers under the quoted licence.
- Ask the municipality/operator whether an existing calibrated model can be shared. Obtaining one with recent source data, reuse rights and validation evidence could change the engine recommendation more than small feature differences.
- Costs and engineering phases require local quantities, surveyed feasibility, unit-rate evidence and responsible design review. No numeric construction budget or guaranteed bus-reliability improvement is inferred from software capability.
